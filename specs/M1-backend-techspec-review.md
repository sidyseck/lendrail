## 1. Top-line verdict

**APPROVED WITH CHANGES**

The spec is well-structured, correctly extends M0, and covers the happy and error paths for all seven backend features. It can go to implementation after the BLOCKER and MAJOR findings below are resolved. None of the blockers require architectural rethinking — all are local fixes to the spec's code snippets or missing guards.

## 3. Decisions — rulings on all 9 open decisions from §10

**Decision 1 — `org_id` non-nullable timeline**

**Ruling: Defer to M2, with a hard gate.** Keep `users.org_id` nullable through M1. At the start of M2, before any M2 migration is authored, a data-validation query must confirm zero rows have a non-NULL `org_id` that does not reference an `organizations` row. If clean, add migration `0005_users_org_id_not_null.py` as the first M2 migration that sets the column `NOT NULL`. `AuthUser.org_id` becomes `UUID` (non-nullable) at the same time, which will require updating `get_current_user` in `deps.py` to raise `AuthError` (not `Forbidden`) for tokens with a null `org_id` — the `AuthError` maps to 401 which is the correct signal for "this token is pre-M1 and no longer valid." Any M0 seed user JWTs issued before this migration are invalidated naturally when the token expires; the login endpoint (`POST /auth/login`) will still work for seed users post-migration only if they have been assigned an `org_id` by then. **Action:** spec engineer adds the M2 gate and migration stub to the M2 spec.

**Decision 2 — `User.role` denormalization**

**Ruling: Keep denormalized through MVP.** The MVP does not expose an org-role-change flow, and there is no admin interface for changing an org's role post-registration in M1 (F-058 only approves/rejects, not changes role). The sync risk is therefore non-existent in M1–M3. Revisit before M4 (loan booking enforces agent role) — if an admin can change org roles between M3 and M4, add a `role` refresh at login. For now: one source of truth (`User.role`), denormalized into JWT. Document the invariant explicitly: `User.role` must equal `Organization.role`; there is no automated enforcement.

**Decision 3 — `ops_contact_email` placement (User vs Organization)**

**Ruling: Move to `Organization`.** The ARCHITECTURE.md data model (`Organization.contact_email`) represents the entity-level contact. `ops_contact_email` is a second entity-level contact for the same org (the operations/settlement desk), not a property of a specific user account. Placing it on `User` creates a problem when the org later has multiple user accounts — which of those users is the ops contact? The migration is trivial: add `ops_contact_email VARCHAR(320) NULLABLE` to `organizations` in migration 0002 (not to `users` in migration 0003). Migration 0003 then does not need to add `ops_contact_email` to `users`. The `User.create_user` method drops the `ops_contact_email` parameter. `OrgService.register_agent` passes `ops_contact_email` to `orgs.create(...)` instead. Update the spec before implementation.

**Decision 4 — Pydantic 422 body format inconsistency**

**Ruling: Standardize to the envelope by adding a `RequestValidationError` handler.** Two different 422 shapes is a client-side integration problem — the frontend (F-014/F-016) and any future API consumers must handle both formats. Add one handler in `register_exception_handlers`:

```python
from fastapi.exceptions import RequestValidationError

async def validation_error_handler(request: Request, exc: RequestValidationError) -> JSONResponse:
    return JSONResponse(
        status_code=422,
        content={"error": {"code": "validation_error", "message": str(exc.errors())}},
    )

app.add_exception_handler(RequestValidationError, validation_error_handler)
```

This also resolves Finding #3 (BLOCKER): once this handler exists, the `model_validator` on `AgentRegisterRequest` can remain as-is and will produce the correct envelope. **Alternatively**, remove the `model_validator` and do attestation-check in the service only — either approach works, but the handler is the more correct fix because it standardizes all future 422s. **Required for M1.**

**Decision 5 — `status` column on `Organization` pre-F-058**

**Ruling: Approved as specced.** Adding `status` in migration 0002 is the right call — it avoids a one-column migration. F-058 is already listed as M1 in the feature index (`FEATURES.md`). The `org_status_enum` and column are in scope and correct. No change needed.

**Decision 6 — `UserRepository` location**

**Ruling: Consolidate into `app/repositories/` in M1, not deferred.** The M1 work already introduces `app/repositories/` as a package. Leaving `UserRepository` in `auth_service.py` while `OrgRepository` and `BorrowerRepository` live in `repositories/` creates an inconsistency that grows worse in M2. The migration cost is low: move the class, update the import in `auth_service.py` and `deps.py`. Add to M1 implementation scope. The spec should mark this as a required M1 task, not a deferred cleanup.

**Decision 7 — Password minimum length**

**Ruling: Raise to 12 characters.** LendRail is a B2B financial platform. NIST SP 800-63B's 8-character floor is the absolute minimum for consumer apps; B2B SaaS and financial services industry practice is 12+. Set `min_length=12` in `SupplierRegisterRequest` and `AgentRegisterRequest`. Update the test that currently uses `"password123"` (10 chars) to use a 12+ char password. No migration or DB change needed.

**Decision 8 — Agent `entity_type` allowed values**

**Ruling: Remove `"agent"` from `EntityType` in the Pydantic schema for the public endpoint.** The `entity_type_enum` in PostgreSQL will retain `"agent"` (it is in the DB ENUM from the architecture data model and removing it is a migration headache). But `EntityType` in `app/schemas/orgs.py` used for the public `POST /orgs/register` request should be `Literal["fund", "corporate_treasury", "foundation"]` — three values, no `"agent"`. An agent lender org that self-registers must pick one of those three entity types (fund, corporate treasury, foundation). The value `"agent"` in the DB ENUM is reserved for any future internal/admin-assigned org that represents an agent lender as an entity type rather than a role. If it is needed in future the schema can be extended. This avoids a confusing UX where an agent registers with `entity_type="agent"` and `role="agent"` — two different concepts using the same word.

**Decision 9 — Auto-approval on registration**

**Ruling: Keep auto-approval (`status="approved"`) for MVP.** The PRD explicitly states "In MVP, orgs self-register and are auto-approved; this endpoint provides manual override capability" for F-058. Requiring admin approval before the JWT is useful would require a second authentication layer (check org status on every request) that is not specced in M0 and adds complexity with zero current value — there are no external users yet. If the product team changes this requirement before external launch, the change is localized to `OrgService.register_*` and a middleware check. Document the assumption explicitly in the spec and add it to the pre-launch checklist.
