## 1. Top-line verdict

**APPROVED WITH CHANGES**

The spec is structurally sound and well-reasoned. Key concerns are: a silent no-op in F-023 (accept writes no state change), a type-safety gap in the F-025 terminate stub, a semantic hole in the UNIQUE constraint around terminated connections, and a missing `model_validator` that would let both F-022 invite fields be omitted at the Pydantic layer. All are fixable without redesign.

## 2. Findings table

| # | Severity | Section | Finding | Required action |
|---|---|---|---|---|
| 1 | BLOCKER | §6.2 F-023 `accept()` | `accept()` calls `self.connections.update(connection, status="pending")` — a no-op write that leaves `status` unchanged. The spec comment says "Status stays pending — it becomes active only after key registration" but there is no intermediate value to distinguish an accepted-but-not-yet-keyed connection from a brand-new invite. The connection ENUM has no `accepted` or `awaiting_key` status, FEATURES.md F-023 says the transition goes to `"pending" (awaiting API key)` which is ambiguous, and the integration test asserts `status="pending"` after both invite and accept — making them indistinguishable to the API consumer. Either add an `accepted` ENUM value (requires schema migration change in 0008) or explicitly document in the spec that the `pending` status is intentionally overloaded and the API consumer must use `activated_at is null && custodian_link_present=false` to infer the accepted-not-yet-keyed sub-state. | Add `accepted` to `connection_status_enum` and transition `pending → accepted` on accept, `accepted → active` on key registration, OR add a prose decision to §10 explaining the overloaded `pending` state and update F-023 acceptance criteria accordingly. |
| 2 | BLOCKER | §3.3, §6 F-021 | The `UNIQUE(supplier_id, agent_id)` constraint on `connections` is permanent and unscoped by status. Once a pair terminates, they can never create a new connection — the `ConflictError(code="connection_already_exists")` will fire on re-invite regardless of whether the old connection is `terminated`. FEATURES.md F-021 says "A UNIQUE constraint prevents two connections rows with the same (supplier_id, agent_id) pair" without addressing the re-connect case, but this is a business logic gap that will hit in practice. | Decide and document in §10: either (a) allow re-invite after termination by scoping the unique constraint to `WHERE status != 'terminated'` (a partial index), or (b) explicitly state re-connection is not supported in MVP and add that guard to the invite service with a distinct error code (`connection_terminated_exists`). |
| 3 | MAJOR | §5.2, §6.2 F-025 terminate | `list_active_by_connection()` returns `list` (untyped), and `TerminateResult.flagged_loan_ids` is `list[uuid.UUID]`. When M4 wires a real `LoanRepository`, it will return `list[uuid.UUID]` but the stub currently returns `list` (actually `[]` which works at runtime). The router then passes `result.flagged_loan_ids` directly to `TerminateResponse.flagged_loan_ids: list[UUID]` — Pydantic will validate this fine with `[]`, but mypy/pyright will flag the `list` → `list[uuid.UUID]` assignment. More critically, `TerminateResponse` has `status: Literal["terminated"]` but the router builds it with `status="terminated"` from `result.status: str` — this is fine at runtime but the `TerminateResult` DTO has `status: str`, not `Literal["terminated"]`, so static analysis cannot confirm it. | Type the stub return as `list[uuid.UUID]` explicitly. Consider typing `TerminateResult.status` as `Literal["terminated"]` to close the gap end-to-end. |
| 4 | MAJOR | §7.1 F-022 | `InviteConnectionRequest` has both `agent_org_id` and `agent_email` as optional fields with no Pydantic `model_validator`. Both can be omitted and Pydantic will accept the request with a 200 parse — the mutual-exclusion guard lives only in the service. This means a malformed request (both `None`) gets past FastAPI validation and only fails at the service layer, breaking the contract that "422 responses use this envelope via the global RequestValidationError handler". A `model_validator(mode='after')` that raises `ValueError` when both are `None` would produce the correct 422 envelope automatically. However, the spec explicitly notes "Mutual-exclusion is enforced in the service (not a model_validator) to ensure the error envelope is always `{"error": {"code": "..."}}`". This reasoning is sound only if the global `RequestValidationError` handler is confirmed to re-wrap `ValueError` from model validators into the correct envelope. If it does, move validation to Pydantic for cleaner code; if it does not, the service approach is correct — but must be documented as an intentional exception to normal Pydantic usage. | Confirm whether the existing `RequestValidationError` handler wraps Pydantic `model_validator` `ValueError`s into the `{"error": {...}}` envelope. If yes, move the mutual-exclusion check into a `model_validator`. If no, add a comment explicitly explaining why it stays in the service, and add a test asserting the error envelope is correct for the missing-both-fields case. |
| 5 | MAJOR | §3.1 migration 0005 | Migration 0005 raises `RuntimeError` when NULL `org_id` users exist, correctly blocking the schema change. However, the existing test fixture pattern (`supplier_headers`, `agent_headers`) registers orgs and users via the API which always sets `org_id`. The risk is test-database seed users created in M0/M1 test setup (e.g., a root admin user, a health-check user, or a pre-M1 legacy fixture) that may have `org_id=NULL`. The migration test `test_0005_migration_fails_on_null_rows` covers the failure path, but there is no test that asserts M1's conftest leaves zero null-org_id users after teardown. | Add an explicit assertion in the M2 conftest (or a dedicated migration test) that runs `SELECT COUNT(*) FROM users WHERE org_id IS NULL` after all M1 fixtures are applied and asserts it equals zero. This guards against any future M1 fixture change introducing a null-org user. |
| 6 | MINOR | §7.2 `get_current_user` | `security.py`'s `create_access_token()` already accepts `org_id: str | None` (the field is typed nullable). After the M2 gate, `AuthUser.org_id` becomes non-nullable `UUID`, but there is no corresponding guard to prevent issuing tokens with `org_id=None` in the first place. The `get_current_user` rejection guard is correct for consuming tokens, but nothing prevents issuing a null-org token and immediately getting a 401 on first use. | Add an assertion or `ValueError` in `create_access_token()` if `org_id is None` after M2 migration 0005 is applied, or document this as an accepted gap since M1 registration always sets `org_id`. |
| 7 | MINOR | §9 test plan F-022 | The test plan includes `test_invite_unknown_email_202` (covers the HTTP 202 + notification case). However, there is no test for the case where `agent_email` is provided and the email belongs to a **registered agent** (i.e., email lookup succeeds, known agent → 201). The table row `test_invite_known_email_201` is listed but its fixture (`agent_email` matching a registered agent org) requires `OrgRepository.get_by_contact_email()` to work correctly — this method is referenced in the service but not mentioned in the repository spec (§5). | Confirm `OrgRepository.get_by_contact_email()` is implemented (it exists in M1's `OrgRepository` per the baseline audit implicitly, but is not shown) and add a test fixture that registers an agent by email and then invites by that email to cover the full code path. |
| 8 | MINOR | §6.2 F-025 `terminate()` | The terminate notification sends only to `caller.user_id`. The spec acknowledges this in §10 item 8 as a known gap — the counterparty is not notified. This is acceptable for M2, but the FEATURES.md F-025 acceptance criterion explicitly states "A `connection_terminated_rotate_key` notification event is logged **for the supplier**" — if the agent terminates, the supplier must also receive this alert. The current code sends it only to the terminating party. | Explicitly flag in §10 item 8 (already noted) that this test case is missing: `test_terminate_by_agent_supplier_also_notified`. Mark it as a M3 enhancement and add the test stub with a `pytest.mark.xfail` or a `# TODO(M3)` comment so it does not silently pass with wrong behavior when M3 wires multi-user notification. |
| 9 | NIT | §6.2 `register_custodian_key()` | `self.secret_store.store(data.plaintext_key)` is called as a sync method (no `await`), but `SecretStore` is described as an async Protocol in §0 ("All adapter Protocols remain `async def`"). If `EnvSecretStore.store()` is sync, the code works but is inconsistent with the Protocol definition. | Verify `SecretStore.store/retrieve/delete` are sync or async and ensure the Protocol definition and all call sites are consistent. |
| 10 | NIT | §6.3 `_sentinel_result()` | Returns a `ConnectionResult` with `id=uuid.UUID(int=0)` (the nil UUID). If this sentinel ever leaks into a test assertion or log, it will look like a real connection ID. A named constant `_NIL_UUID = uuid.UUID(int=0)` with a comment would make the intent clearer. | Low priority; cosmetic only. |

## 3. Must-fix checklist (BLOCKER / MAJOR only)

- [ ] **#1 F-023 accept state machine:** Resolve the `pending → pending` no-op — either add `accepted` to the ENUM (migration 0008 change) or add a documented §10 decision explaining overloaded `pending` semantics and update acceptance criteria.
- [ ] **#2 UNIQUE constraint + re-invite after termination:** Decide and document the re-connect policy; implement a partial index or an explicit `connection_terminated_exists` guard in `invite()`.
- [ ] **#3 Terminate stub type safety:** Tighten `list_active_by_connection()` return type to `list[uuid.UUID]` and consider `TerminateResult.status: Literal["terminated"]`.
- [ ] **#4 InviteConnectionRequest validation placement:** Confirm or deny that the global `RequestValidationError` handler wraps `model_validator` errors; document the decision explicitly and add the missing envelope-format test.
- [ ] **#5 Migration 0005 null-org guard:** Add a conftest assertion that no null-org_id users exist after M1 fixture setup, to prevent future regressions.
