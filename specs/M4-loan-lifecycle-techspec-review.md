## Executive Summary

The M4 spec has the right high-level direction: backend first, layer boundaries, latest dual-confirmed agreement guard, org-level custodian handling, and no frontend work before backend contracts stabilize. However, it currently reads as a greenfield implementation spec while this checkout already contains partial M4 backend files (`0011_loan_lifecycle.py`, `loan.py`, `loan_repository.py`, `loan_service.py`, `loans.py`, worker wiring). That creates a real handoff risk: a frontend engineer or second backend engineer could follow the spec and believe contracts exist that the current code does not implement.

The highest-risk gaps are missing transition audit contracts, mismatched response field names, incomplete approved-borrower semantics, custodian mock contracts that cannot test failure/idempotency, and lifecycle state definitions that diverge between the spec, `FEATURES.md`, and the current implementation.

## Architecture Alignment Notes

- The spec is aligned with the M2/M3 redesign that removed `connections.custodian_link_id` and made custodian links supplier org-level. Keep that. Do not reintroduce connection-level custodian state for M4.
- The spec is aligned with M3's latest-agreement guard: booking must use `get_latest_for_connection()` and distinguish no agreement from latest unconfirmed. Keep that distinction.
- The spec's use of the architecture's "agreement-defined LTV" formula matches `ARCHITECTURE.md` and `FEATURES.md`, even though the naming is financially awkward. Keep the formula for acceptance-test compatibility and label it carefully in code comments.
- The architecture says the LTV refresh worker is the autonomous path to margin-call state. M4 should not implement active-loan margin-call thresholding, but M4 should not make APIs incapable of handling a loan already in `margin_call`.

## Backend-First Gate

F-042 frontend work should not begin until these backend items are true:

1. Migration `0011` and ORM models match the final M4 DB contract, including the decision on transition audit and approved-borrower `approved_by`.
2. `LoanService`, repositories, routers, and worker use the same field names as `LoanResponse`.
3. Backend tests cover F-033 through F-041, including duplicate approved borrower, latest unconfirmed agreement, insufficient inventory, failed return instruction, worker activation idempotency, non-terminal loan flagging on termination, and response privacy.
4. Mock custodian and market data adapters are seedable enough for all M4 success/failure paths.
5. `frontend/openapi.json` and any generated/manual frontend types are refreshed after backend contract freeze.

## Suggested Correction Order

1. Resolve spec deltas first: agreement minimum loan size, transition audit table vs timestamp-only, custodian collateral ref, and response field names.
2. Reconcile existing backend implementation with the corrected spec before adding frontend code.
3. Add backend tests and migration roundtrip coverage.
4. Regenerate/update OpenAPI and frontend API types.
5. Implement F-042 UI against the frozen backend contract and MSW fixtures.

## Final Technical Lead Recommendation

Do not treat `specs/M4-loan-lifecycle-techspec.md` as implementation-ready yet. It is a strong draft, but it needs a reconciliation pass against the already-present M4 backend files and several hard contract decisions. The largest risk is not the domain model; it is contract drift between spec, backend responses, worker behavior, and the frontend types that will be built next.
